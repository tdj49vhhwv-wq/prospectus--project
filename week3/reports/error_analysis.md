## Q5: 单位错误如何发现 (股、万股、元、万元)

### 当前检测方法

1. **Pydantic Schema注释**: 每个数字字段有description标注单位
   ```python
   shares_subscribed: Optional[float] = Field(None, description="认购数量（万股）")
   amount_subscribed: Optional[float] = Field(None, description="认购金额（万元）")
   ```

2. **Cross-check 价格×数量≈金额**: 当三个字段都有值时自动校验
   - 友升A轮: 8.3333元/股 × 840万股 ≈ 7,000万元 ✓
   - 友升B轮: 33.6323 × 297.3333 ≈ 10,000万元 ✓
   - 三协电机: 5.41 × 321.50 = 1,739.315 ≠ 1,723.09 (差异0.9% → 待复核)

3. **量级检查**: 增资后注册资本/总股本与认购数量对比
   - 出资额从500→5000万时,单次出资不应超过5000万

### 未被发现的单位错误

**当前盲区**: Auto提取中shares_subscribed和price_per_share字段全部为None,导致cross-check无法执行。

| 风险 | 场景 | 影响 |
|------|------|------|
| 万股/股混淆 | PDF写"1000万股",auto可能提取1000(万股)or1000(股) | ×10,000误差 |
| 万元/元混淆 | PDF写"7000万元",auto可能提取7000(万)or7000(元) | ×10,000误差 |
| 美元/人民币混淆 | 赛分科技"170万美元" vs "7000万元" | 汇率折算 |
| 出资额(market value)vs注册资本(par value) | 增资溢价部分 | 出资额≠注册资本增加额 |

### 改进方案

- LLM识别单位关键词: "万股"/"万元"/"亿美元"等
- Pydantic validator增加量级合理性检查: 单次增资>50亿→flag
- 同一事件内所有数字统一单位后再cross-check

## Q6: 股权转让如何和增资认缴分开

### 三个层次的分离

**1. Schema层 (数据结构)**:
```python
# 增资认缴
SubscriptionFlow.subscriber_name     # 认购方(谁出钱)
SubscriptionFlow.shares_subscribed   # 认购数量

# 股权转让
ShareTransferFlow.transferor_name    # 转让方(谁卖出)
ShareTransferFlow.transferee_name    # 受让方(谁买入)
ShareTransferFlow.shares_transferred # 转让数量
ShareTransferFlow.transfer_amount    # 转让价款
```

**2. 人工Gold层 (PDF阅读)**:
- 证据中关键词"认购""增资"→subscription_flow
- 证据中关键词"转让给""转让予""将其持有...转让"→share_transfer_flow
- 7条股权转让已从124条增资中分离: 黄山谷捷3条(同一控制下零对价), 赛分科技1条(业绩补偿), 影石创新1条(申报前调整), 星图测控2条(代持还原)

**3. Auto提取层 (规则)**:
- 当前规则只覆盖增资,未单独提取股权转让
- 事件类型通过event_context字段区分
- 规则改进方向: 新增转让关键词正则(`转让给\|转让予\|将其.*转让`)

### 边界case处理

- **增资+转让同时发生**: "三联有限第三次增资及股权转让" → Gold拆为4行subscription_flow(event_context="增资及股权转让")+股权转让行
- **收购vs转让**: 赛分有限收购美国赛分 → 非股权转让,是公司收购(M&A),已排除
- **增资后内部股东调整**: 同一事件中既有新认购(外部进入)又有老股东转让(内部调整) → subscription_flow+share_transfer_flow各一行

## Q7: cross-check失败后流程如何处理

### 当前处理流程

```
cross-check发现差异(price×shares≠amount或持股合计≠总股本)
  ↓
标记status="待复核" (不修改数据,不删行)
  ↓
记录difference数值和detail说明到 cross_check_summary.csv
  ↓
写入 manual_review_queue.csv (P0/P1/P2优先级)
  ↓
人工回到PDF页面验证:
  - 确认PDF原文数值
  - 检查是否单位混淆(股/万股/万元)
  - 检查是否四舍五入差异
  ↓
两种情况:
  A. PDF自身数据不一致 → 保留差异,notes注明"PDF数据矛盾"
  B. 提取/计算错误 → 修正Gold数据,重新生成JSONL
```

### 当前待复核项 (2项)

| # | 公司 | 差异 | 原因 | 处理 |
|:--:|------|------|------|------|
| 1 | 三协电机 | price×shares=1739≠1723(差16万) | PDF自身:拟募集1739万,实际收到1723万 | 保留,标"PDF数据矛盾" |
| 2 | 友升股份 | 认购合计1100万≠出资额变化13640万 | 单位混淆:股改净资产折股,认购股数≠出资额 | 标注为正常差异(股改事件) |

### 待复核但当前未检出的潜在问题

当前cross-check仅14行,因为auto数据的价格/数量字段全部为None。Gold数据中以下场景无法校验:
- 无total_shares字段的快照: 无法验证持股合计≈总股本
- 无price_per_share的事件: 无法验证价格×数量≈金额
- 相邻快照间缺少中间时点: 无法追踪股东变化

## Q8: 如果扩展到50家公司,最先会失败在哪里

### 失败点优先级 (从最早到最晚)

**P0 — 立即失败**:

1. **PDF格式多样性** (预计覆盖<30家)
   - PyMuPDF输出差异: 不同PDF生成工具的文本提取质量不一致(扫描件/图片PDF完全无法提取)
   - MinerU/PyMuPDF输出格式不兼容: 友升股份用MinerU导致snapshot=0
   - 红筹/VIE架构: 融资历史不在"股本演变"章节(影石创新、预计3-5家)
   - **失败表现**: 章节定位返回空,自动提取输出0行

2. **投资人名称多样性** (预计覆盖<40家)
   - 纯英文名(外资基金): CASREV, IDG, Sequoia, GIC → regex 0%覆盖
   - 政府/国资平台: "国家集成电路产业投资基金二期股份有限公司" → 长度超regex限制
   - 个人投资者: 无"有限/合伙/基金"后缀 → regex 0%覆盖
   - **失败表现**: 投资人名称全部漏提

**P1 — 中期失败**:

3. **事件表述多样性** (预计覆盖<35家)
   - "发行股份购买资产"(并购重组)→ 不含"增资"关键词
   - "资本公积转增股本"(公积金转增)→ 不含"增资"但含"转增",可能误判
   - "股权激励"(员工持股)→ 不含"增资"关键词
   - "债转股"(债务重组)→ 关键词"转"+"股"非"增资"
   - **失败表现**: 30-50%事件漏提

4. **单位/币种混淆** (扩大到所有公司)
   - 港股/红筹公司: 港币/美元计价的增资
   - 早期公司: 注册资本按"万元"、后期按"亿元"
   - **失败表现**: cross-check全部0匹配,单位不可比

**P2 — 后期失败**:

5. **Cross-check失效** (价格/数量字段缺失)
   - 50家中约60%的增资事件不披露price_per_share(仅披露总金额)
   - 价格×数量≈金额 校验覆盖率不足
   - **失败表现**: cross_check_summary.csv行数不足,无法验证数据质量

6. **人工复核瓶颈**
   - 8家43事件 → 50家约270事件
   - 人工回到PDF逐项验证: 每个事件5-10分钟 → 270×7=~32小时
   - **失败表现**: manual_review_queue堆积,event停留在"待复核"状态

### 扩展前必须解决的3个问题

1. PDF解析统一: 所有公司统一使用PyMuPDF输出(带`## 第N页`标记),放弃MinerU
2. 投资人名称扩展: 正则+LLM混合(规则提取中文名,LLM补充英文名+消歧)
3. 单位标准化: 提取后统一转换为"万元人民币",在evidence中保留原始单位
