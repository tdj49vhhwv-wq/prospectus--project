## 模型与清洗审计

建模前固定日期、50%收缩标签、算法家族选择规则和10%预算。算法家族仅按交易T基线的验证AP选定，再在同一LR家族检验新增公开信息，避免混淆算法更换与数据增量。验证期交易基线优于增强组合，当前商业建议保留交易基线，并非将测试略高的增强方案自动部署。

首次计算后进行原始事件时序复核，发现61笔配送早于批准、20条评价早于批准。前者时间改为未知，后者剔除，按照原固定方案重跑所有模型，不选择更好分数。`initial_metrics_before_timestamp_audit.csv`保留纠错前全部模型结果，正式报告只用纠错后的结果。

更晚月份核对的日期与固定模型规则在查看主结果前保存；核对前重新拟合同一训练＋验证集合，并确认原测试预测与原模型完全一致。没有使用主测试标签更新模型。更晚窗口与主窗口有商户和时间重叠，不能冒充独立复验。

## 业务闭环

信息可用性分流 → 交易排序形成核查名单 → 评价及履约定位待核实线索 → 独立确认经营与真实结算 → 记录误报、失访、耗时、干预与后续信用表现 → 用时间外样本评价增量与净价值 → 通过才扩大，否则保留画像并回退人工补资料。

该产品闭环属于待执行设计。当前可验证的结论是交易排序对未来平台经营收缩线索比低评分更有效，并不能证明增加公开评价已创造增量商业收益。
