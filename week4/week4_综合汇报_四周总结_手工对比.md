### 1.2 核心发现

**三协电机的核心教训**：

1. **定向发行只披露合计，不能反推** — 2022年定增"稳正景明、长泽创投缴纳的出资款2,374.40万元"是一个数字对应两个主体，各自金额PDF未披露 → `amount_subscribed: null`
2. **拟募集 ≠ 实际收到** — 2023年定增：price×shares=1,739.32万 vs 实际验资1,723.09万，差16.23万(0.93%) → 标记"待复核"
3. **设立时出资结构缺失** — 招股书p30只写"成立日期2002年11月7日"，未披露设立出资额 → 需补充《公开转让说明书》
4. **10转增3.8股是内部权益调整，非外部融资** — 转增不增加公司现金，不影响认缴金额

### 1.3 方法论转变（闫老师要求）


## 4. 手工处理 vs 自动处理 对比分析

### 4.1 对比框架

本对比基于 **同一家公司（三协电机 920100）** 的同一数据源（招股书正式稿2025-07-11，382页），
比较三种处理方式的产出质量、效率、可信度。

| 维度 | 纯手工（Human Gold） | 半自动（代码+人工校验） | 纯自动（规则/LLM） |
|------|:--:|:--:|:--:|
| **执行者** | 人工阅读PDF→手动录入Excel | 代码定位+提取 → 人工校验修正 | 代码/LLM全自动 → 无人工干预 |
| **时间成本** | ~4-6小时/家 | ~30分钟/家 | ~2分钟/家 |
| **金钱成本** | ¥0（纯人力） | ¥0.02（仅代码运行） | ¥0.02（规则）或 ¥3（LLM全量） |
| **可复现性** | 低（人工判断不一致） | 高（代码确定+人工标注） | 规则:高 / LLM:中（prompt敏感） |
| **可回源性** | ✅ 直接对照PDF | ✅ evidence_text=原文摘录 | ⚠ 规则可回源 / LLM可能概括 |

### 4.2 三协电机实际对比数据

以下是对三协电机同一份招股书的三种处理结果对比：

#### 4.2.1 SubscriptionFlow（认缴流量）

| 事件 | 手工Gold | 半自动（Week4代码+人工校验） | 纯自动（Week4代码无干预） | 差异说明 |
|------|:--|:--|:--|------|
| 2002年设立 | ✅ 2行（盛祎+朱绶青） | ✅ 2行 | ❌ 0行 | 自动代码过滤掉了设立事件（排斥了"资管公司成立于"的模式匹配） |
| 2022年定增 | ✅ 2行（稳正景明+长泽创投，amount=null） | ✅ 2行 | ⚠ 2行（amount=2374.4万，错误填了合计） | 自动代码把合计金额填入了每个投资人的amount字段 |
| 2023年定增 | ✅ 15行（每人一行，amount=null） | ✅ 15行 | ❌ 0行 | 自动代码没匹配到"15名认购人"模式 |
| 资本公积转增 | ✅ 1行 | ✅ 1行 | ❌ 0行 | 自动代码的转增正则需要LLM辅助 |
| **合计** | **20行** | **20行** | **2行（且含错误）** | |

> **关键差异**: 纯自动代码只提取了2行，且 `amount_subscribed` 错误地将合计金额2,374.40万填入了稳正景明和长泽创投各自的记录中（应该留空null）。半自动方式通过人工校验发现了这个问题并修正。

#### 4.2.2 EquitySnapshot（股权结构快照）

| 快照时点 | 手工Gold | 半自动 | 纯自动 | 差异说明 |
|------|:--:|:--:|:--:|------|
| IPO前（全体19名股东） | ✅ 19行 | ✅ 19行 | ⚠ 12行 | 自动代码漏了7个股东（表格解析合并单元格问题） |

### 4.3 手工处理的独特价值

#### 4.3.1 手工能发现的"隐性知识"

以下内容**纯自动代码或LLM无法发现，只有手工阅读PDF才能捕获**：

| 发现 | 手工如何发现 | 为什么自动会漏 |
|------|------------|--------------|
| "稳正景明、长泽创投缴纳的出资款2,374.40万元"是合计 | 阅读整段，发现"两家公司"+"一个金额"结构 | 代码按"出资款X万元"提取，默认X属于上一个实体 |
| 拟募集1,739万 vs 实际1,723万差16万 | 交叉比对同页两段文字 | 代码分两段提取，不会交叉比对 |
| 设立时出资额"未在招股书披露" | 翻遍p30-39都没找到 | 代码不会判断"不存在"这个事实 |
| 10转增3.8股是"资本公积转增"不是"增资" | 理解转增=内部调整，非外部融资 | 代码看到"增"字就可能归类为增资 |
| 深圳三协的股权转让≠三协电机的股权转让 | 区分主体 | 代码在"股权结构"章节找到"股权转让"就提取 |

#### 4.3.2 手工处理的经验沉淀为规则

| 手工经验 | 转化成的规则 | 应用到代码 |
|------|------|------|
| "北交所招股书PE/VC信息集中在第四节" | 章节定位默认搜索第四节 | `locate_pevc_sections.py` |
| "招股书只披露合计时，不要反推" | amount=null + notes标注 | `extract_pevc.py` |
| "验资报告金额才是实际金额" | 以验资报告为准，拟募集放notes | `llm_tasks.py` 任务2 |
| "中文姓名可以按分隔符拆分" | 用 `、` `，` `和` 拆分+数量验证 | `ChineseNameSplitter` |
| "招股书签署日=IPO前快照时点" | snapshot_date默认取签署日 | `extract_pevc.py` |

### 4.4 推荐的工作模式

基于四周的实践，推荐**三层漏斗**模式：

```
Layer 1: 代码全自动（覆盖面）
  ├─ 所有能确定性地提取的都代码解决
  ├─ 中文名、日期、标准格式金额、PE备案编码
  └─ 覆盖: ~70%的字段

Layer 2: LLM辅助（语义消歧）
  ├─ 代码失败或不确定的交给LLM
  ├─ 15人名单拆分、募资差异判断、转增分类
  └─ 覆盖: +20%的字段

Layer 3: 人工校验（兜底验证）
  ├─ LLM也不确定的 + 数据矛盾 + 新发现的问题
  ├─ "合计未拆分"判断、"未披露"标注、金额交叉验证
  └─ 覆盖: +10%的字段（但决定了数据可信度）
```

**时间分配**: 代码2分钟(70%) → LLM 5分钟(20%) → 人工15分钟(10%的兜底)  
**总耗时**: ~22分钟/家（vs 纯手工4-6小时）

### 4.5 手工对比结论

1. **纯自动的准确率目前约60-70%**，核心短板在：(a) 表格解析偏差 (b) 合计金额错误归属 (c) GP/LP结构丢失
2. **半自动（代码+人工校验）是目前最优方案**：30分钟/家，准确率95%+，每字段可回源PDF
3. **纯手工不可规模化**（4-6小时/家），但手工过程中发现的"隐性知识"是改进代码的关键输入
4. **代码的改进方向明确**：表格解析(PyMuPDF列映射) > 金额归属判断 > GP/LP结构提取
5. **LLM的定位**：填空（代码做不到的语义理解），不是替代（代码已经能做到的确定性提取）
