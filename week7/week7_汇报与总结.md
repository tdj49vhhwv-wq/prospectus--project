## 一、本周做了什么（6 天）

### Day 1：读懂一家公司的融资故事

- 逐页阅读赛分科技（688758）招股书第 50-62 页；
- 梳理“设立—员工激励—机构进入—股改—Pre-IPO 增资—转增”的完整路径；
- 认识到提取任务不能只看代码是否运行，必须理解事件、投资人和资金流的经济含义。

### Day 2：Gold Standard 124 条逐条对照

- 对照 `subscription_flow_gold.jsonl` 与原文；
- 发现旧 PDF 管线只输出 18 条，且原有正则在 Gold 原文上仅能命中 7 条；
- 归纳出资、认购、折股、股权转让、吸收合并等主要漏提模式；
- 同时发现星图测控 7 条员工持股平台记录更接近股权快照，Gold 分类口径需要修订。

### Day 3-4：扩充规则并做 LLM 小样本试验

- 新增多类正则后，在 Gold 原文上的规则命中达到 82/124；
- 对 10 段困难原文进行 DeepSeek 试验，返回 21 条候选；
- 这些数字只证明规则和 LLM 能发现更多候选，尚不能作为 Precision、Recall 或 F1。

### Day 5：建立 Markdown 文本源

- PDF 缺失时，从 `week1/review` 下的 MinerU/PyMuPDF Markdown 读取文本；
- 8 家公司均可定位到相关段落；
- 当前代码仍存在路径、输入版本和运行日志没有完全固定的问题。

### Day 6：全量复跑并检查误报

- 当前代码在 325 个 Markdown 片段上稳定生成 645 条原始候选；
- 其中 214 条无日期、311 条无金额、637 条无股数、全部缺少价格；
- 投资人字段出现“法定代表人”“注册地址”等明显误报；
- 结论：管线已经“能跑”，但还没有达到“可信可用”。

## 二、对前期问题的反思

### 我之前偏了的方向

1. 花了较多时间在数据库可视化、目录整理和输出条数比较，但这些不能证明提取准确；
2. 把规则在 Gold 原文上的命中数误写成 Recall，没有独立计算 TP、FP、FN；
3. 把 10 段 LLM 小样本的补漏结果外推为“100%覆盖”，证据不足；
4. 让宽松正则直接生成正式记录，没有把“候选”与“最终数据”分开；
5. 代码中曾硬编码 API Key，说明安全和工程规范没有进入验收清单。

### 这周真正纠正的

1. 先逐条读 Gold 和招股书原文，再判断规则为什么漏提；
2. 区分 Pipeline 输出数、Gold 规则覆盖数和严格评价指标；
3. 通过全量复跑主动暴露误报，而不是只汇报输出数量增加；
4. 确认 Week 8 的第一任务应是评价器与 Gold 口径，而不是继续堆正则；
5. 将密钥改为环境变量，将 Markdown 路径改为仓库相对路径。

## 三、当前结果应该如何表述

| 层级 | 当前结果 | 能说明什么 | 不能说明什么 |
|------|------|------|------|
| 旧 PDF Pipeline | 输出 18/124 条 | 旧管线漏提严重 | 不能直接等同严格 Recall=14.5% |
| Gold 原文规则实验 | 命中 82/124 条 | 新规则覆盖表达更多 | 不能证明独立样本泛化能力 |
| LLM 小样本 | 10 段返回 21 条 | LLM 有补漏潜力 | 不能宣称全量达到 100% |
| Markdown 全量复跑 | 645 条原始候选 | 8 家文本源均可运行 | 候选存在大量误报，不能直接入 Final |

本周最重要的进展，是从“有没有输出”转为追问“输出是不是对的、错在哪里、能否复跑”。

## 四、需要老师确认的问题

1. **Gold 分类口径**：星图测控 7 条员工持股平台记录的证据是 IPO 前持股结构，是否同意通过变更日志将其从 `subscription_flow` 评价口径迁移到 `equity_snapshot`？
2. **主评价单位**：是否同意同时报告事件级指标与投资人明细级指标，而不是只报告总条数？
3. **文本源选择**：短期用仓库内 Markdown 建立可复跑评价；PDF 恢复后再做页码和表格证据复核，是否可接受？
4. **LLM 使用边界**：先由正则生成高置信度结果，LLM 只处理低置信度候选；所有 LLM 结果仍需进入同一评价器，是否可接受？
